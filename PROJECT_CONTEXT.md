# КОНТЕКСТ ПРОЕКТА: PWA «Отчет Экспедитора»

> **Назначение файла:** Первый источник правды (First Source of Truth) для передачи контекста в новые сессии разработки. При перезапуске чата передается вместе с системным промптом и целевыми файлами для правок.
> **Актуальная версия кодовой базы:** v3.3 (архитектура без обратной совместимости, скрытая дедупликация, модальное подтверждение).
> **Пакет файлов версии:** `index.html`, `app.js`, `appsscript.js`, `manifest.json`, `sw.js`.

---

## 0. САМОЕ ВАЖНОЕ (прочитать перед любой правкой)

1. **`Content-Type: text/plain;charset=utf-8`** — НЕ менять на `application/json` (CORS-preflight, который Google Apps Script не поддерживает, заблокирует все POST-запросы).
2. **Версия кэша SW:** при любом изменении `app.js` или `index.html` обязательно поднимать версию в `sw.js` (`driver-pwa-v11`, `v12` и т.д.), иначе клиенты не получат свежий JS/HTML из-за кэша.
3. **Удаление отчета из очереди телефона** — ТОЛЬКО после явного `{status: 'success'}` от бэкенда с учётом ошибок СЕТИ или исключений.
4. **Сжатие фото:** декодирование через `createImageBitmap` / Blob-URL с принудительным `bmp.close()` / `revokeObjectURL`. Использование `FileReader.readAsDataURL` для оригиналов запрещено из-за риска OOM-краша браузера.

## 1. БИЗНЕС-ЛОГИКА И СТЕК ТЕХНОЛОГИЙ

*   **Назначение:** Мобильное веб-приложение (PWA) для полевых экспедиторов: фиксация визита в торговую точку (8 атрибутов то ТЗ);
*   **Специфика:** Полная автономность в подвалах и на трассе без связи с отложенной гарантированной автовыгрузкой;
*   **Архитектурная модель:** Offline-First (запись в локальную базу на диск → подтверждение записи → фоновая отправка в сеть при появлении связи → удаление из базы телефона);
*   **Технологический стек на данный момент v3.3:**
    *   *Фронтенд:* Vanilla JavaScript (ES6+), HTML5, CSS3 (без сборщиков и фреймворков).
    *   *Хранилище клиента:* IndexedDB (очередь отчетов), LocalStorage (`drv` — сохраненное ФИО водителя).
    *   *Офлайн-оболочка:* Service Worker (кэширование каркаса приложения).
    *   *Бэкенд:* Google Apps Script (Web App, `doPost(e)` — прием отчетов, `doGet(e)` — пинг доступности).
    *   *Хранилище:* Google Sheets (лист = ФИО экспедитора), Google Drive API v3 (папка с фото).
*   **Актуальный рабочий GAS_URL:**`(https://script.google.com/macros/s/AKfycbyceW1oRstLa5Vq4HBZOJG-4pgln0Z1GbflV2tuvbsAd-lgQtLw62fNXAzMTVLPbQv9/exec)`

*   `pointName` — поле торговой точки (обязательное).
*   `meter` — показания счетчика (`type="text" inputmode="numeric" pattern="[0-9]*"`).
*   `smallToys` — мелкие игрушки (шт).
*   `zamanukha` — заманухи (шт).
*   `probros` — проброс (текст).
*   `problems` — проблемы на маршруте (`<textarea>`).
*   `photo` — выбор фото (`<input type="file" accept="image/*" multiple>`).
*   `photoLimit` — подпись максимального количества фото (связана с `MAX_PHOTOS`).
*   `photoList` — контейнер динамических превью выбранных фото с кнопками удаления (`✕`).
*   `submitBtn` — главная кнопка отправки данных.
*   `status` — блок текстового информирования о состоянии очереди и сети.
*   `confirmOverlay` — подложка модального окна подтверждения отправки (`.hidden` переключает видимость).
*   `confirmSummary` — блок текстовой сводки отчета перед подтверждением.
*   `confirmYes` — кнопка «ДА» в модальном окне.
*   `confirmNo` — кнопка «НЕТ» в модальном окне.

### 3.2. База данных IndexedDB (`app.js`)
*   `DB_NAME`: `'DriverReportsDB'`
*   `DB_VERSION`: `2` (Версия 2: добавлен обязательный числовой индекс `by_created` по полю `createdAt`).
*   `STORE_NAME`: `'reports_queue'`
*   `keyPath`: `'id'` (строка формата `rep_${Date.now()}_${random5}`)
*   **Схема объекта отчета в очереди (v3.3):**
```javascript
    {
      id: string,            // Уникальный ID отчета (передается как reportId на сервер)
      user: string,          // ФИО водителя
      pointName: string,     // Наименование точки
      meter: string,         // Показания счетчика (строка, сохраняющая нули)
      smallToys: string,     // Мелкие игрушки
      zamanukha: string,     // Заманухи
      probros: string,       // Проброс
      problems: string,      // Описание проблем
      photos: string[],      // Массив Base64-строк (от 0 до MAX_PHOTOS)
      timestamp: string,     // Локализованная строка времени для отображения на экране
      createdAt: number,     // Время заполнения в мс по часам телефона (Date.now())
      retries: number,       // Число неудачных попыток отправки
      lastError: string|null,// Текст последней ошибки
      failed?: boolean       // true только у отложенных «ядовитых» отчетов
    }
```

### 3.3. Сетевой контракт API (`app.js` ↔ `appsscript.js`)
*   **Транспорт POST:** `headers: { 'Content-Type': 'text/plain;charset=utf-8' }`.
*   **Формат полезной нагрузки (JSON stringify):**
```json
    {
      "action": "REPORT",
      "reportId": "rep_1761213015000_a8x2q",
      "user": "Иванов Иван",
      "pointName": "Магнит У дома",
      "meter": "00451",
      "smallToys": "12",
      "zamanukha": "3",
      "probros": "0",
      "problems": "Нет",
      "createdAt": 1761213015000,
      "photos": ["/9j/4AAQSkZJRg...", "..."]
    }
```
*   **Форматы ответов бэкенда (всегда HTTP 200, Content-Type JSON):**
    *   *Успешная запись:* `{"status": "success", "row": 15, "sheetName": "Иванов Иван"}`
    *   *Дубликат отсечен:* `{"status": "success", "duplicate": true, "sheetName": "Иванов Иван"}`
    *   *Отказ с классификацией:* `{"status": "error", "code": "VALIDATION|BUSY|SERVER", "message": "Причина"}`

### 3.4. Структура Google Таблицы (`appsscript.js`)
*   Имя листа = санитизированное ФИО экспедитора (спецсимволы `\/*?:[]'` заменяются на `_`, длина до 50 символов).
*   Шапка таблицы (`A1:H1`, ровно 8 колонок, закреплена, жирный шрифт, фон `#e8f0fe`):
    1. `A: Дата и время создания` — время заполнения отчета (форматируется сервером из `createdAt` в `dd.MM.yyyy HH:mm:ss` по `SERVER_TZ`).
    2. `B: Торговая точка` (`data.pointName`).
    3. `C: Показания счетчика` — текст, сохраняются лидирующие нули (`data.meter`).
    4. `D: Мелкие игрушки` — число (`Number(data.smallToys) || 0`).
    5. `E: Заманухи` — число (`Number(data.zamanukha) || 0`).
    6. `F: Проброс` (`data.probros || ''`).
    7. `G: Проблемы на маршруте` (`data.problems || 'Нет'`).
    8. `H: Фото` — многострочный `RichTextValue` («📷 Фото 1», «📷 Фото 2»...) с гиперссылками на Google Диск, либо текст ошибки загрузки фото, либо «Без фото».
*   *Колонка «ID отчета» в таблице отсутствует* — защита от дубликатов перенесена в скрипт.

## 4. ПОВЕДЕНЧЕСКИЕ ПОЛИТИКИ И АЛГОРИТМЫ

### 4.1. Алгоритм отправки и подтверждения (v3.3)
1. **Шаг 1 (Валидация полей):** Проверяется заполненность ФИО и Точки. Формируется текстовая сводка.
2. **Шаг 2 (Модальное окно):** Показывается `#confirmOverlay`. При нажатии «НЕТ» или Esc окно закрывается, форма сохраняется нетронутой.
3. **Шаг 3 (Обработка после «ДА»):**
   * Блокируется кнопка `submitBtn`.
   * Фотографии сжимаются строго по одной (освобождая память между кадрами).
   * Фиксируется метка времени `createdAt = Date.now()`.
   * Формируется объект отчета и сохраняется в IndexedDB (`await dbPut(item)`).
   * Очищается форма ввода и сбрасывается массив выбранных фото.
   * Если сеть доступна — немедленно инициируется цикл выгрузки очереди (`syncQueue()`).

### 4.2. Алгоритм выгрузки очереди и изоляция сбоев
*   Выгрузка защищена от конкурентности через `navigator.locks.request('driver-report-sync')` (с фоллбэком на `isSyncing`).
*   Курсор `dbPeekOldest()` перебирает записи по индексу `by_created`, пропуская записи с флагом `failed === true`.
*   Страховка от зацикливания: `handledInCycle = new Set()` внутри сессии синка гарантирует, что один отчет обрабатывается не более 1 раза за цикл.
*   **Изоляция сбоев:**
    *   Если сервер вернул `code === 'VALIDATION'` (неисправимая ошибка содержимого), отчет помечается `failed = true`, сохраняется в базе и откладывается, а цикл выгрузки переходит к следующему отчету (`continue`).
    *   При временных ошибках (сеть, код `BUSY`, код `SERVER`) цикл прерывается (`break`), отчет остается активным первым кандидатом на выгрузку при следующем сетевом событии.

### 4.3. Серверная обработка и защита от дублей (v3.3)
*   **Probe Lock (Fail-fast):** Попытка взять замок на 1 секунду. Если сервер перегружен, мгновенно отдается `jsonError('BUSY')` без траты ресурсов на загрузку фото.
*   **Загрузка фото:** Выполняется ВНЕ блокировки таблицы. Каждое фото грузится в Drive независимо, сбой отдельного фото не отменяет запись строки.
*   **Атомарный блок (30 сек):**
    1. Захват `LockService.getScriptLock()`.
    2. Поиск/создание листа водителя.
    3. Проверка `dedupHas(safeName, reportId)`. Если найден — возврат `{status: 'success', duplicate: true}` без повторной записи строки.
    4. Запись строки в таблицу.
    5. Формирование кликабельных ссылок через `RichTextValue`.
    6. `SpreadsheetApp.flush()`.
    7. Фиксация `reportId` в памяти скрипта через `dedupRemember()`.
    8. Освобождение блокировки в `finally`.

## 5. ИЗВЕСТНЫЕ РИСКИ И ТЕХНИЧЕСКИЙ ДОЛГ (BACKLOG)

1.  **[Критично / Память GAS]:** Реализация `dedupRemember` через `PropertiesService` хранит сериализованный JSON в одном свойстве (лимит свойства — 9 КБ). При приближении к 120 ID возможно падение с ошибкой превышения размера. Рекомендуется плановый переход на `CacheService` или возврат скрытой колонки в таблицу.
2.  **[HTML]:** В файле `index.html` отсутствует начальный доктайп `<!DOCTYPE html>` и открывающий тег `<html>`, что может переводить мобильные браузеры в Quirks Mode.
3. РЕАЛИЗОВАНА ЛИ? защиты от дублей строк:**  
    Если произошел ERR_TIMED_OUT, это не значит, что сервер ничего не сделал! Сервер мог успеть записать строку в таблицу, а связь оборвалась ровно в момент отправки ответа клиенту. Телефон, получив ошибку, отправит отчет повторно — в таблице появится дубль.
4. #### Конфликт setNumberFormat и appendRow (Счетчик и пустые строки)
- **Файл:** appsscript.js, строки 261–280.
    **В чём суть:**
    codeJavaScript
    ```
    var nextRow = sheet.getLastRow() + 1;
    sheet.getRange(nextRow, 3).setNumberFormat('@'); // ШАГ 6
    
    sheet.appendRow([ ... ]); // ШАГ 7
    ```
    **Анатомия сбоя:**
    
    1. Метод sheet.appendRow() в Google Apps Script ищет **первую строку, в которой нет никаких данных**.
        В зависимости от версии движка Google Таблиц, применение метода .setNumberFormat('@') к ячейке пустой строки nextRow может перевести эту ячейку в статус «инициализированной». В этом случае следующий за ним sheet.appendRow() вставляет данные **на строку ниже (nextRow + 1)**, оставляя между отчетами пустые «дыры».
        Более того: метод appendRow **автоматически распознает типы входных данных**. Если в массив передана строка цифр "0057", appendRow при вставке игнорирует формат ячейки и вставляет ее как число 57.
5. Скрытые поля в таблицу добавлять нельзя. #### Переполнение квоты PropertiesService и бесконечный цикл дублей в Таблице
- **Файл:** appsscript.js, функции dedupRemember(), dedupHas(), строки 59–108.
- **В чём суть:**  
    Вы решили убрать служебную колонку «ID отчета» из таблицы и сохранять историю отправленных reportId в PropertiesService.getScriptProperties() с ключом seen_Водитель.  
    В коде задан лимит: const DEDUP_MAX_IDS = 120;.
- **Анатомия сбоя (Физика квот Google Apps Script):**
    1. В Google Apps Script действует **жесткое ограничение на размер одного свойства: ровно 9 КБ (9 216 байт)**, а в бесплатных аккаунтах суммарный объем всех свойств скрипта ограничен **500 КБ** (в некоторых типах контейнеров — теми же 9 КБ на весь скрипт).
    2. Объект из 120 строковых ключей формата "rep_1761213015000_x3k2a": 1761213015000 в сериализованном виде занимает **~5.5–6 КБ**.
    3. Как только у вас появится 2–3 активных водителя, суммарный размер свойств превысит системную квоту.
    4. При вызове PropertiesService.getScriptProperties().setProperty(...) Google выбросит фатальный exception: Exception: Argument too large: value или Exception: Total size of properties exceeded.
- **Катастрофические последствия:**  
    Посмотрите, где вызывается dedupRemember:
    codeJavaScript
    ```
    SpreadsheetApp.flush(); // Строка уже записана в Таблицу!
    dedupRemember(safeName, data.reportId); // <--- ЗДЕСЬ ПАДАЕТ EXCEPTION!
    ```
    Строка в таблицу **уже добавлена**, но скрипт падает на dedupRemember, улетает в catch и возвращает телефону ответ: { status: "error", message: "Argument too large" }.  
    Телефон видит ошибку, оставляет отчет в очереди и **отправляет его снова**. Скрипт снова пишет строку в таблицу и снова падает на dedupRemember.  
    **Итог:** За 5 минут в таблицу запишется 50–100 дубликатов одной и той же строки, пока на телефоне не кончится лимит ретраев или не зависнет скрипт.
- **Как исправить:**  
    Хранить ID отчетов в PropertiesService нельзя. Самое надежное и бесплатное хранилище — сама Таблица. Если колонку нельзя показывать пользователю, ее делают скрытой (скрыть столбец в Google Таблице), либо используют CacheService (он имеет лимит 100 КБ и автоматически очищается сам без риска краша скрипта).
